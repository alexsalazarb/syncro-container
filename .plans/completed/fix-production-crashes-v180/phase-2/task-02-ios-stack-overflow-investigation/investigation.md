## Step 2 — Breadcrumb correlation (weak signal, not proof)

Both crash samples show `new_open_attachments_detail` in their last few breadcrumbs before the crash:
- Sample 1 (`27de086c...`): `open_ticket_detail → ticket_tab_notes → tapped_create_new_note → open_ticket_detail → open_attachments_detail → [gap] → open_attachments_detail (again) → UIDocumentPickerViewController → CRASH`. Also has a log line right before: `"Socket failed after 3 attempts."`
- Sample 2 (`bb466325...`, fetched earlier in this session): `open_tab_home → open_tab_tickets → open_ticket_detail → open_attachments_detail → open_attachments_detail (again) → CRASH`

**This looked like a strong lead** (attachment-related screen opened twice in a row before crashing in both samples) but two things weaken it:
1. `rg -rn "new_open_attachments_detail"` and `rg -rln "new_open"` across `lib/` return **zero matches** — this event name is not fired by our own code with that literal string. It's very likely auto-generated by a third-party product-analytics SDK (Pendo is integrated in this app — see `SE-12785-pendo-sdk-upgrade`) that synthesizes screen-view event names from UI/route metadata, not a 1:1 mapping to our route names (`attachment-preview` route, `ticket_attachment` feature). So "attachments_detail" may not correspond exactly to the files I inspected.
2. The `"Socket failed after 3 attempts."` log traced cleanly to `chat_websocket_service.dart:652` — but that function's retry loop (lines 602-648) is a plain iterative `for` loop, not recursive, and I found no caller that recursively re-invokes `connect()`/`_tryInitialConnection()`/`_handleNetworkReconnection()` in a cycle. Most likely this log is just something that happened moments earlier in the session (an unrelated background reconnect attempt), not causally related to the crash.

## Files inspected and ruled out (no recursion found)

- `lib/core/services/chat_websocket_service.dart` — `connect()` (iterative retry loop, correctly bounded by `maxRetries`), `_tryInitialConnection`, `_handleNetworkReconnection`, `_performHealthCheck`, `_onZoneError` — traced the full call graph between these five methods; no cycle where any of them calls back into a method that (directly or transitively) calls itself.
- `lib/features/ticket/ticket_attachment/presentation/attachment_preview_view.dart` — trivial `StatelessWidget`, single flat `build()`, no recursive calls, no navigator push loop.
- `lib/features/ticket/ticket_attachment/presentation/ticket_attachment_view.dart` and `ticket_attachment_page.dart` — no `setState`-in-`build`, no self-referential navigation, nothing that would recurse.

## Blocker: no symbolication available

The crash's exception frames are raw addresses (`_kDartIsolateSnapshotInstructions+0x...`) with **no Dart symbol names** — Crashlytics could not resolve them, meaning the historical release build(s) that produced this crash (app versions 1.4.0 through 1.7.0) were not uploaded with a matching Dart obfuscation/debug-info map (`flutter build ... --split-debug-info=<dir>` + the corresponding `dart symbolize` step), or that artifact wasn't retained.

Checked this repo for a build pipeline that generates one: no `--split-debug-info`/`--obfuscate` flag found anywhere in tracked scripts/CI config, and no local `symbols`/`debug-info` directory exists in this checkout. Without the matching debug-info bundle for the exact build (version + build number) that produced these events, the raw offsets **cannot be decoded to real function names** — I have no way to identify the actual recursive call site from here.

## What would unblock this

1. **Going forward**: add `--split-debug-info=<path>` (and ideally `--obfuscate`) to the release build command, and archive the generated symbol files per build number so future crashes in this category are automatically symbolicated by Crashlytics (or symbolicate-able after the fact via `flutter symbolize`).
2. **For this specific issue**: if anyone on the team has a local/CI archive of the `.symbols` output for build 441 (v1.7.0) or earlier builds where this fired, running `flutter symbolize -i <crash-file> -d <symbols-file>` against the raw stack trace above would very likely reveal the actual function.
3. Absent either of those, the only remaining path is speculative code review across every place in the app that does recursive-shaped work (recursive `copyWith`/`toJson`, self-referential widget rebuilds, Cubit-emits-triggering-its-own-listener patterns) — not attempted here because it would be a guess, not a confirmed fix, and this plan's own instructions explicitly warn against skipping straight to a fix without a confirmed root cause.

## Recommendation

Do not guess a fix. Checked `crashlytics_get_report(report: "topVersions", issueId: ...)` for this issue: **0 events on 1.7.1 (443) and 0 on 1.8.0** — the two most recent releases. All 35 events in the 90-day window are on 1.7.0 (441, 24 events) and 1.6.1 (433, 11 events); nothing since 1.7.0 shipped (roughly 2.5 months of zero recurrence as of this investigation). Combined with the symbolication blocker above, chasing this further right now has a poor cost/benefit: no way to confirm a fix even if one were attempted, and the issue is not currently reproducing.

Closing this task as **blocked/monitoring** rather than complete — the root cause is genuinely unknown, so this is not a resolved bug, just a dormant one. Escalate to the team: (a) add `--split-debug-info` to the release pipeline so *any future* recurrence is symbolicate-able, (b) leave the Crashlytics issue OPEN (do not close — it hasn't been fixed, it's just stopped happening for reasons we don't understand) and revisit only if new events appear on 1.7.1+/1.8.0+.
